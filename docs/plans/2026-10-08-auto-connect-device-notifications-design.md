# 自动连接与设备加入通知

日期：2026-10-08。实现基线：`origin/main` / `5283472fd76113b6526c4aa76fbc4038c1f0e9e4`。

## 用户体验

1. 启动后发现局域网设备，设备列表呈现实际发现状态；首次发现提示用户查看设备并连接。
2. 本端点击连接表示本端同意加入。首次接收入站连接时，对端看到待批准请求、设备身份和完整证书指纹；批准后发起端重新点击连接。
3. 双方握手成功后，通知“设备已加入”。设备已有明确批准且证书保持一致时，后续发现、断线和服务重启可自动重新连接。
4. 短暂断线后的成功连接提示“设备已恢复连接”。发现广播、心跳和界面刷新不会重复提醒。
5. 点击断开后，该设备在当前守护进程生命周期内暂停自动连接，也不能由对方立即重新接入；本端点击连接恢复许可。
6. 设置中提供“自动连接已批准设备”和“设备加入通知”。保存后立即生效，并在重启后保留。

## 信任与连接策略

自动连接的资格来自 QUIC 信任文件中的 `OperatorApproved` 证书记录。`security.trusted_devices` 中的 ID、主机名、发现广播和旧 `LegacyTofu` 记录都不能替代明确批准的证书。

自动拨号检查使用实际 `QuicTransport` 的信任文件路径，测试仍使用隔离目录。读取错误时跳过自动连接。资格检查通过后，TLS 和应用层 Hello/HelloBack 仍验证证书及目标 ID；发现地址或名称改变不能覆盖原有 pin。

首次入站和旧 TOFU 入站进入现有 `PendingApprovalRegistry`，未获得匹配批准时关闭连接。批准令牌绑定设备 ID 与完整证书指纹，有效期两分钟且仅使用一次。只有匹配的后续握手才持久化操作员批准并发布认证连接。等待用户确认不占用守护进程的网络管理锁。

已有认证连接不因关闭自动连接开关而被断开；开关只影响后台拨号。证书变化、协议不兼容和损坏的信任文件不会触发自动批准或覆盖证书。

## 调度与断开

`NetworkManager` 管理后台拨号；桌面关闭后守护进程仍执行连接策略。

- 每个设备最多一个后台尝试；保留 1、2、4、8、16、32、60 秒上限的退避。
- 发现状态用于选择当前地址；检查现有认证连接后才拨号。
- 开关和手动断开抑制状态在已排队任务拿到连接锁后重新检查。
- 手动连接解除该设备的抑制；手动断开的抑制也传到入站认证发布路径。
- `DeviceLost` 不删除失败历史，也不直接代表认证连接断开。
- 连接代次继续使用原有生命周期检查，旧连接的迟到断开不能影响新连接。
- 双方同时拨号时，用出站尝试的生命周期标记识别碰撞，较小设备 ID 的一端拒绝反向入站候选，保留统一方向；只有一端发起连接时仍正常接受。

## 配置与本地接口

持久化配置新增 `network.auto_connect_trusted`，默认 `true`，旧配置缺字段时保持该默认。普通通知使用已有 `gui.show_notifications`。

```rust
PeerConnectionSettings {
    auto_connect_trusted: bool,
    notify_device_events: bool,
}
```

本地 IPC 新增：

| 请求 | 响应 | 作用 |
| --- | --- | --- |
| `GetPeerConnectionSettings` | `PeerConnectionSettings` | 查询守护进程当前策略 |
| `SetPeerConnectionSettings { settings }` | `PeerConnectionSettings` | 保存成功后热更新 |
| `GetLocalPeerIdentity` | `LocalPeerIdentity` | 当前运行实例的设备 ID 和完整证书指纹 |
| `ListPendingPeerApprovals`（已有） | `PendingPeerApprovals` | 列出待批准设备 |
| `ApprovePeer { approval_id }`（已有） | `Ack` | 发放匹配证书的一次性加入许可 |

设置写入由守护进程序列化，先加载现有配置，仅改变这两个字段，以同目录临时文件写入、同步后原子替换配置，保存成功后再改变运行状态。保留已有文件权限。加载或保存失败返回错误，保留其他配置。启动时配置损坏会禁用后台自动连接。

待批准查询和批准操作使用独立的注册表句柄，不等待后台 QUIC 拨号锁。设置页面显示当前实际 TLS 身份的完整指纹，便于双方核对。

## 通知与界面

通知只观察已接收的守护进程设备投影，连接状态以认证连接为准。纯模型保留已发现/当前连接/曾连接设备集合，用于判断发现、首次加入和恢复连接。

- 第一个权威快照静默建立基线；已有设备不会在打开窗口时批量弹出。
- 守护进程 `boot_id` 变化重新建立基线；重复 delta、重同步和轮询更新不能重复提示。
- 设备重命名、地址刷新和 `last_seen` 更新不生成加入通知。
- 通知关闭期间仍更新模型；重新开启时只提示此后的变化。
- 移除设备清除当前在线状态，保留会话中的历史加入信息。
- 待批准请求有明确确认界面，不依赖普通通知开关决定是否可见。

前台通过全局应用内提示呈现，桌面在后台或托盘运行时通过 Tauri 原生通知插件呈现。桌面完全退出后，守护进程仍执行连接策略，通知需待桌面运行。原生桥接从守护进程验证设备状态，避免直接显示任意前端标题；系统通知不执行批准。系统通知受操作系统权限控制，拒绝权限时仍可在应用中查看设备和批准请求。

原生插件接入依据：[Tauri Notifications](https://v2.tauri.app/plugin/notification/)。

## 验收

- 未批准设备和旧 TOFU 设备无法后台连接或静默加入；损坏信任文件不能放行。
- 正确证书的已批准设备可以自动连接及恢复；证书变化拒绝。
- 同一设备广播多次只有一个后台尝试，失败退避不因发现丢失而重置。
- 双方同时重连仍保留稳定认证连接，不能因各自关闭重复候选而互相断开。
- 关闭开关阻止排队后台尝试；手动断开阻止双方重新接入，本端连接恢复。
- 待批准令牌过期、重复使用、错误证书和错误设备 ID 不能建立认证连接。
- 初始快照、重连流、轮询、重命名、boot 变化和通知开关变化不造成重复提示。
- 多设备加入分别呈现，前台/后台通知不重复；普通通知关闭后仍可操作加入审批。
- 设置旧配置兼容、往返序列化、保存失败和其他字段保留通过测试。

自动化验证覆盖策略、握手和通知模型；真实双机、睡眠唤醒以及各平台通知权限需要手动验证。
