# 跨设备文件拖拽

## 从本机文件夹直接拖到另一台电脑的文件夹

1. 两端更新并重启新版 daemon 和桌面应用，连接设备、配置屏幕布局，先确认鼠标可以跨屏。
2. 在另一台电脑的 Finder 或资源管理器中打开目标文件夹。
3. 在本机 Finder／资源管理器中抓起文件或文件夹，按住鼠标左键，越过配置好的屏幕边缘。
4. 在远端文件列表的空白处，或一个实际文件夹图标上松手。文件会复制到该位置，保留原文件及目录结构。
5. 两端的 **设备 → 文件传输** 显示进度和错误，可取消传输；接收完成后可打开目标文件夹。

这里模拟的是文件夹之间的复制手势：不会删除本机源文件，也不会覆盖远端已有文件。同名文件自动保存为 `报告 (2).txt`，同名文件夹保存为 `资料 (2)`。暂不显示远端系统原生的文件拖拽缩略图，也不向邮件、编辑器等其他应用发送系统原生拖放事件。

macOS 读取系统本次拖拽会话，使用辅助功能识别落点。如果 Finder 不提供窗口地址，会按已识别窗口的位置与大小读取 Finder 的文件夹信息，可能需要在 **系统设置 → 隐私与安全性 → 自动化** 中允许 R-ShareMouse 访问 Finder。不会通过普通剪贴板里的旧文件列表猜测拖拽来源。

Windows 使用资源管理器的选中项和鼠标起点识别源文件，使用 UI Automation 与 Shell 文件夹信息识别落点。需使用系统资源管理器的普通文件夹窗口。存在无法唯一识别的标签页、虚拟位置或缺失的权限时会拒绝投放；识别失败不会改存到下载目录。

按 Escape、松手前返回本机、目标断线或控制会话更换，会作废尚未提交的手势。跨入另一台远端设备时应松手后重新开始拖拽，不会沿用前一个设备的落点。

## 拖到应用内设备卡片

在桌面应用的 **设备 → 文件传输** 区域，将文件拖到目标电脑卡片即可发送。此入口也适用于 Linux。接收目录为系统下载目录下的 `R-ShareMouse/<传输编号>/`；每次使用独立目录。普通浏览器仅支持查看进度和取消，不能提供原生文件路径。

## 边界与故障处理

- 单次最多 1024 个文件和目录、总大小 10 GiB；最多 4 个活动传输。
- 支持中文名、二进制文件、空文件和空目录。拒绝符号链接、特殊设备文件、目录穿越、Windows 保留名称以及不区分大小写的路径冲突。
- 直接跨屏文件夹拖拽目前实现 macOS 和 Windows；Linux、桌面区域、搜索结果、最近使用、虚拟文件夹和其他应用窗口不在支持范围内。
- 接收端在目标目录中的隐藏临时目录写入并逐文件校验 SHA-256。完整收到后逐个顶层项目发布，使用系统原子“不覆盖”重命名。多项目发布过程中如果遇到磁盘错误，已发布项目保留，未发布部分清理，任务报错并保留目标目录入口。
- 取消、断线、块顺序错误、大小或校验不符会结束任务并清理未完成内容。单次网络收发等待超过 30 秒会失败；不支持断点续传。最终发布开始后取消可能来不及阻止已完成的文件落盘。
- 不要在传输期间修改源文件；校验保证本次发送和接收的字节一致，不提供源文件的原子快照。
- 最后确认丢失时，接收端可以已经完成、发送端却显示失败。重新拖拽会生成新副本，不会覆盖。
- 最近 64 条记录由 daemon 在内存中维护。重启后记录清空、文件保留。强制终止进程或掉电可能留下 `.partial-*` 目录，确认没有活动传输后可清理。

## 实现与验证

直接拖拽：本机左键按下 → 移动至少 8 个坐标单位 → 跨屏 Enter → 捕获源文件并结束本机系统拖拽 → 远端松手 → 文件服务 OfferToFolder → 接收端验证实际注入成功的松手事件 → 本机识别目标文件夹 → QUIC 传输、校验与发布。

落点凭据绑定设备、本次连接、输入会话、松手序号与坐标，10 秒内仅可消费一次。目标路径由接收端本机查询，不接受发送端指定的任意目录。输入线程只传递有限的手势事件；原生查询、文件枚举和收发在独立工作任务中完成。

两端协商 `file_transfer_version=1` 和 `folder_drop_version=1`。文件内容使用优先级低于键鼠的 QUIC Bulk 通道，以 64 KiB 块传输并逐块确认；任务绑定本次连接，旧连接的数据不能进入重连后的任务。

```bash
cargo test -p rshare-core -p rshare-input -p rshare-net -p rshare-daemon --locked -- --test-threads=4
cargo check -p rshare-daemon --target x86_64-pc-windows-gnu --locked
npm test --prefix apps/rshare-desktop-frontend
npm run build --prefix apps/rshare-desktop-frontend
```

原生只读探针：`cargo run -p rshare-platform --example folder_drop_probe -- target X Y`，坐标采用系统桌面坐标。`source X Y 30` 在 30 秒内观察一次测试文件拖拽；探针不注入输入、不发送文件。macOS 下 `windows` 可读取 Finder 窗口位置，方便验收坐标换算。

2026-09-07 验证结果：core/input/net/daemon 的 Rust 测试 902 项通过、1 项既有 LAN 发现测试忽略，另有桌面端 Rust 测试 44 项通过；其中 10 项真实 QUIC 文件回归覆盖文件夹投放、同名保护、无效落点拒绝及已有收发/取消场景。前端 256 项通过并构建成功。Windows daemon 交叉编译通过，资源管理器脚本通过 PowerShell 语法解析。

Finder 原生验证已观察到系统拖拽会话中的测试文件路径，并验证文件夹图标、图标视图空白区、列表视图空白区及空文件夹的目标识别；普通文件与侧边栏落点被拒绝。该验证使用本机临时测试文件，不代表两台物理设备已经完成拖拽验收。

一次并行编译期间，既有网络控制消息测试发生 1 秒超时；单独重跑和降低测试并行度后的完整受影响测试均通过，失败日志保留。当前 daemon 未发现在线对端，也未替换正在运行的旧 daemon；双方更新后的实际跨屏手势、Windows Explorer 运行时、多显示器 DPI、传输期间键鼠响应及断网恢复仍需双机验收。日志位于 `target/file-drop-validation/2026-09-07/folder-drag/`。

全工作区 Release 构建、受影响模块的普通 Clippy 和格式检查通过；Clippy 仍有既有告警。Chrome 的 2 个界面回归通过，包含失败后保留接收目录入口的场景。

本机 Chrome 回归首次受代理环境影响，预览服务虽然返回 HTTP 200，但测试启动检测超时；仅对该次本地测试移除代理变量并设置 `NO_PROXY=localhost,127.0.0.1` 后通过。未修改系统或 Cargo 的全局代理配置。
